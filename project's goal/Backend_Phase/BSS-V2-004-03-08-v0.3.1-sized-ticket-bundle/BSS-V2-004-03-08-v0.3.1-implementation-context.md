### 0.4 Context-only image disposition: hard decision gate

The experiment represented the image-only title/legend using `classification="non_fact"`, `candidates=[]`, and an explanatory `non_fact_reason`. This is intelligible **as an experiment** under the binary `candidate | non_fact` output contract, but the reason is untrusted provider prose and **not** a durable Atlas-owned evidence/context relationship. It would be unsound to assume that text-only `non_fact_reason` makes screenshot-derived synthetic scope available to later knowledge reasoning.

**Proposed bounded resolution without Semantic V2:** establish an Atlas-authored, validated, versioned **context-provenance sidecar** independent of provider-proposed candidates. It records source context roles (e.g., legend/interpretation, illustrative scope, header applicability), origin source slot/page/locator/asset hash, *which owned assertions it governs*, and the trusted relationship permitting cross-slot application. Model-proposed context interpretation remains untrusted until validated against original authorized media and a reviewed source-context oracle. Context-only input may still appear as `non_fact` **solely in the candidate-inventory sense** (no independent assertion), with a bounded explanatory reason; it must not mean that meaningful context was discarded. The sidecar does **not** constitute new business truth, new canonical candidate, or another provider source-results enum.

**Do not declare the sidecar designed/approved yet.** `08-01-02` must decide and prove the representational fit against existing `03-03` accounting and the planned `03-05` validation contract; implementation proof is owned later by `08-02-01` and `08-03-02`, including exact visible title and `?`/legend provenance. If context cannot survive, or Atlas cannot deterministically validate its correct propagation, record **SCHEMA_FIT_BLOCKED** and seek bounded HMN: either authorize an explicit additive context/evidence contract or revise the split. Do not silently reclassify it as a fake `business_object`, add `contextual` as a third enum, or claim a CK PASS. Never allow an otherwise unreadable meaningful image to become `non_fact` merely because the image was not delivered.

### 0.6 Decision: stepwise changes the *new* prompt-builder contract, not the legacy contract

**YES: leaf `08-01-04` owns an additive prompt-builder contract that deterministically renders the v0.3.1 eight-step semantic interpretation process.** The eight stages are a reviewed instruction *ordering and responsibility contract*, not a second definition of 16 semantic kinds, a guaranteed model-internal chain-of-thought trace, a provider-specific feature, or permission to repair a response. The output remains one final provider proposal; do not request hidden reasoning, stage-by-stage intermediate output, or expose chain-of-thought.

The new compiler must expose versioned metadata for **stage identity/order**, each stage's source authority (`ZOD_SEMANTIC`, `ZOD_SOURCE_INPUT`, `STATIC_POLICY`), the rendered section hash, and the overall new profile/prompt/schema identity. Freeze the eight stage identities below in order:

1. `understand_evidence_context`
2. `identify_independent_propositions`
3. `preserve_normalize_meaning`
4. `select_primary_semantic_kind`
5. `assess_uncertainty_clarification`

The compiler may render canonical field descriptions within their owning stage or use references to a single Zod-derived section. It **must not** maintain a hand-copied duplicate enum or re-define canonical `kind`, `payload`, `normalized_meaning`, `needs_resolution` or question meanings in new fixed strings. **Legacy remains the default:** Existing calls to `compileExtractionPrompt()` and `buildSemanticSourcePacket()` continue returning their approved text-only profile, structure, ordering, hashes, and failure behavior. The stepwise multimodal path requires an **explicit new profile selection**; no global default flip, silent fallback, runtime auto-switch, or changed semantics of an existing profile ID. Do not assume the current text-only packet can transmit image pixels just because a new prompt is available. The new profile is inactive until downstream authorization.

### 14.2 Evidence-status vocabulary

- `OBSERVED_MANUAL`: result actually present in immutable manual provider evidence; not a production PASS.
- `PROPOSED_DESIGN`: a recorded source-fit or implementation proposal, not itself an accepted architectural/policy change; bounded existing work can start by direct GO.
- `OFFLINE_PASS`: deterministic test evidence at an exact reviewed SHA only.
- `MODEL_QUALITY_PRELIMINARY`: human/fixture semantic review without repeatability or real-PDF qualification.
- `RAW_CONTRACT_FAIL`: fenced/non-JSON or invalid enum/shape before authoritative parser/finalizer.
- `SCHEMA_FIT_BLOCKED`: V1 plus authorized contextual evidence cannot represent material meaning faithfully; require HMN.
- `BASELINE_UNVERIFIED`: parent-HEAD legacy prompt/packet/contract tests cannot be independently reproduced; shared edits blocked.
- `LEGACY_REGRESSION_BLOCKED`: changed code altered approved legacy behavior unexpectedly; isolate or obtain owner amendment + CK.
- `OWNERSHIP_CONFLICT_BLOCKED`: two tickets claim a single mutable auth, adapter or finalizer owner; freeze and escalate.
- `CROSS_LEAF_SCOPE_BLOCKED`: GO/CFC grows into another leaf or two independently mutable boundaries; split via HMN.
- `RESOURCE_ENVELOPE_BLOCKED`: conservative image limits/tokens cannot be established.
- `FIXTURE_UNAVAILABLE_BLOCKED`: original evidence bytes, SHA, inventory or reviewer access cannot be independently verified.
- `SOURCE_RELATIONSHIP_BLOCKED`: essential table↔image/legend relation has no Atlas-authorized source.
- `PROVIDER_NOT_AUTHORIZED`: a real inference request is outside the permitted zero-call scope of every `08` leaf.
- `READY_FOR_CK`: one bounded leaf has complete observed RC and current-SHA regression evidence, awaiting independent review.
- `CK_PASS`: independent reviewer verified **that leaf only**, not model reliability, whole workstream, or live admission.
