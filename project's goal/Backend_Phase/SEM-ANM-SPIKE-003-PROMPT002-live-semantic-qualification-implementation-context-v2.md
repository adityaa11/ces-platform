## 11. Semantic Oracle Philosophy

The oracle evaluates **material business meaning**, not exact natural-language phrasing.

Harmless wording variation is allowed.

Do not require byte-equal:

```text
customer / the customer
order / an order
submit / submits
```

Do require preservation of:

```text
primary semantic role where materially clear
actor/object identity
modality
negation
numeric values
limit direction
units
scope
conditions
temporal ordering
resolution state
presence/absence of invented meaning
```

For free-form provider payload, do not require one exact payload key vocabulary unless the frozen schema itself requires it.

The oracle may inspect:

```text
kind
needs_resolution
normalized_meaning
semantic_key
all recursively present payload keys/values
questions
```

using bounded deterministic comparison helpers.

Do not use another LLM, embeddings, fuzzy semantic search, or semantic repair in the oracle.


### 11.1 Deterministic surface normalization for oracle comparison

The oracle may use the same narrow surface normalization principle proven in the historical spike, **comparison-only**:

```text
trim leading/trailing whitespace
lowercase for comparison
collapse repeated whitespace
remove harmless surrounding punctuation
remove one leading English article:
  a
  an
  the
```

Examples that must compare as equivalent where the underlying semantic identity is unchanged:

```text
customer
the customer

order
an order
the order

acceptance criterion
the acceptance criterion
an acceptance criterion
```

A small source-anchored grammatical inflection check may also be used where necessary, for example:

```text
submit
submits
submission
```

This normalization must never mutate:

```text
raw provider content
JSON sent to Zod
validated provider proposal
persisted evidence
```

It exists only to prevent harmless articles/grammar from causing a false oracle failure.

It must not normalize away material semantic differences such as:

```text
customer -> supervisor
order -> invoice
maximum -> minimum
2 -> 3
required -> possible
per order -> per customer
```

## 21. Terminal Classification

Use exactly one:

```text
PASS
PASS_WITH_LIMITS
FAIL
ENVIRONMENT_BLOCKED
```

`PASS` requires both equivalent calls to pass parse, exact Zod validation, exact source accounting, and all S1-S4 semantic invariants without semantic repair.

`PASS_WITH_LIMITS` requires all correctness conditions for PASS while recording a material operational limitation such as fence dependence, latency, reasoning/token overhead, cost, or non-correctness-breaking routing behavior.

`FAIL` is used when inference executes but output, validation, accounting, or semantic invariants fail.

`ENVIRONMENT_BLOCKED` is reserved for credential, entitlement/rate, outage, network, or environment failures that prevent meaningful inference.
