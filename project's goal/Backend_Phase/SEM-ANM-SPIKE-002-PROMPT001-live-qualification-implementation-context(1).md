## 9.1 Semantic Oracle Acceptance Philosophy

The semantic oracle must evaluate **preservation of business meaning**, not byte-for-byte lexical equality of free-text fields.

The provider is allowed harmless surface variation when the meaning is unchanged.

Examples that must not fail solely because of wording:

```text
customer
the customer

order
an order
the order

submit
submits
submission

before processing
approval occurs before processing
```

The oracle must therefore distinguish:

```text
STRICT / MATERIAL
    semantic kind
    enum meaning
    resolution state
    numeric values
    limit direction
    actor/object/target identity
    applicability vs temporal distinction
    scope
    presence or absence of invented meaning

TOLERANT / SURFACE
    leading English articles
    capitalization
    harmless whitespace
    surrounding punctuation
    grammatical inflection
    concise source-faithful paraphrase that preserves the same proposition
```

This tolerance is not authority to use a second LLM or broad semantic-repair layer.

A bounded deterministic comparison normalizer may be used for oracle comparison only.

At minimum it may:

```text
trim
lowercase
collapse internal whitespace
remove harmless surrounding punctuation
remove a leading English article:
  a
  an
  the
```

A small deterministic inflection/lemma comparison may be used only when it preserves the source-anchored lexical meaning.

The comparison helper must **not mutate the provider proposal** before Zod validation or Atlas finalization.

Do not use semantic-equivalence tolerance to excuse material changes such as:

```text
customer -> supervisor
order -> invoice
submit -> approve
possible -> permitted
possible -> required
maximum 2 -> maximum 3
per order -> per customer
before processing -> if processing begins
missing applicability condition -> invented condition
```

If a materially different proposition is produced, the run fails even if the wording is fluent.

## S1

```text

```

Required semantic invariants:

```text
semantic_kind = workflow_step
actor semantically identifies the customer
action preserves the submit/submission meaning
object semantically identifies the order
resolution_status = resolved
clarification_question = null
```

Harmless surface forms such as:

```text

order / an order / the order
submit / submits / submission
```

must not fail the oracle solely because of articles or grammatical form.

The result must not require clarification merely because the source omits incidental details such as:

```text
submission method
storage
transport
order contents
exact timing
downstream behavior
```

## S4

```text

```

Required semantic invariants:

```text

modality = possible

applicability_conditions do not invent a trigger
resolution_status = needs_resolution
clarification_question asks only for the missing material applicability condition
```

The temporal wording does not need to be lexically identical.

For example, both of these may be acceptable when they preserve the same ordering:

```text

```

Likewise, clarification wording may vary, for example:


The result must preserve:


