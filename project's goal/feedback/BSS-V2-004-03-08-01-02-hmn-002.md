## Diagnosis and exact verdict

**Semantic V1 classification fit passes conditionally.** One table-owned candidate may be grounded by both its table locator and a meaningful visual title/legend locator without creating a second visual-owned business assertion:

1. the table source-inventory item is `candidate` and names the table-owned local candidate;
2. the visual source-inventory item is also `candidate` and names that **same** local candidate;
3. the one candidate's `evidence_refs` contains both locators; and
4. the additive relationship record below, not either source classification, authorizes contextual propagation.

This is faithful because `candidate` means that a source establishes project meaning; it does not mean that the source exclusively owns a candidate. `atlasSemanticExtractionResultV1Schema` permits several inventory destinations to name the same local candidate, and `PostgresExtractionAcceptanceHandler` requires every inventory locator attributed to that candidate to occur in its evidence references. The result is one table-owned assertion with dual attributable evidence, not a visual-owned duplicate.

The alternatives remain distinct:

| Source situation | V1/source disposition | Context-provenance disposition | Semantic result |
| --- | --- | --- | --- |
| Duplicate/decorative visual with no project meaning | `non_fact`, bounded structural reason | none | no visual-owned assertion |
| Verified title/legend materially qualifying a table assertion | `candidate`, pointing to the existing table-owned local candidate | accepted relationship, `essential` or `optional` as attested | one dual-evidence table-owned candidate |
| Meaningful visual with no verified interpretation or relationship | do not emit a falsely completed V1 extraction result for it | `deferred` / `RELATIONSHIP_UNRESOLVED` | dependent assertion is blocked or deferred; independent sources remain eligible |

Thus a meaningful visual is never marked `non_fact` just to satisfy accounting. If it cannot be interpreted or its required relationship is unverified, it remains an upstream deferred source and an essential dependent assertion cannot be marked complete.

## Minimal additive contract

The proposed immutable revision is **`atlas.context-provenance/v1`**. It is an Atlas-controlled sidecar record; it is not a Semantic V1 candidate, kind, source-classification value, provider field, or substitute for original evidence.

```text
ContextProvenanceRelationshipV1 {
  contract_version: "atlas.context-provenance/v1"
  relationship_id: bounded opaque Atlas ID
  scope: { project_id, workspace_id, document_id, source_sha256 }
  normalized_document: {
    execution_id, capability_identity, contract_version, profile_id_or_version
  }
  owned_source: { page_number, locator_type: "table", locator_id, source_unit_id }
  owned_candidate: { extraction_execution_id, local_candidate_id }
  context_source: {
    page_number, locator_type: "visual_region", locator_id, source_unit_id,
    asset_ref, derived_asset_sha256
  }
  relationship: {
    type: "context_qualifies",
    direction: "context_source_to_owned_candidate",
    contextual_role: "title" | "legend",
    necessity: "essential" | "optional"
  }
  relationship_evidence: [
    { role: "owned_source_evidence" | "context_source_evidence" | "attested_binding",
      page_number, locator_type, locator_id, excerpt_digest? }
  ]
  issuer: { issuer_type, issuer_identity, attestation_id, authorization_basis }
  validator: { identity, version, result, validated_at, rejection_code? }
  revision: positive integer
  relationship_hash: sha256(canonical immutable relationship fields)
  disposition: "accepted" | "rejected" | "unresolved"
}
```

`relationship_hash` is SHA-256 over canonical JSON of every immutable field above except `relationship_id`, `validated_at`, validator runtime metadata, and `relationship_hash` itself. The scope, normalized-document execution, source SHA, locator identities, `asset_ref`, derived hash, role/necessity, issuer attestation, evidence identities, and revision are included. Any duplicate hash in its scope is idempotent; a different record for the same owned candidate/context role must be rejected as duplicate or contradictory rather than silently superseded.

## Issuer, validator, and lifecycle policy

The only qualified issuer is an **explicit Atlas human evidence attestation**: `atlas.hmn.human_evidence_attestation/v1`. It is not a reviewer role, provider identity, derived-asset resolver, NormalizedDocument locator, or fixture declaration. Its authorization basis must be an immutable user-delegated HMN/planning decision naming the exact project/workspace/document/source SHA, both locators, role, necessity, and evidence identities. The present user delegation authorizes this contract design and offline qualification; it does **not** issue a runtime relationship for arbitrary documents.

The validator must bind the issuer's named identity tuples to the accepted NormalizedDocument and accepted derived manifest, verify the table-owned candidate's two evidence references, recompute the canonical hash, and enforce uniqueness/contradiction rules. It may validate an attested relationship; it may never infer one. A provider or model may describe a proposal, but cannot issue, approve, or upgrade a relation.

Lifecycle is fail-closed:

`proposed -> unresolved | rejected | accepted`

Only an accepted record may supply visual context to its named table-owned candidate. `unresolved` is required for missing attestation or incomplete authority; `rejected` is required for bad scope/SHA/asset/locator, mismatch, duplicate conflict, or invalid issuer. For an essential relation, either state blocks the dependent assertion with `SOURCE_RELATIONSHIP_BLOCKED` / `RELATIONSHIP_UNRESOLVED`; for optional context, the candidate may proceed without applying the context and the omission remains recorded. Neither state creates a new candidate or turns meaningful material into `non_fact`.
