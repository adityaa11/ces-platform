## Diagnosis

The frozen `BSS-V2-014-05` contract and parent gate both describe a replacement of an already active v1 IDSER consumer. The source does not support that premise. `createIdserProspectiveCapacitySnapshotConsumer()` is an exported historical v1 library factory (`apps/agents-bridge/src/idser-prospective-capacity-snapshot.ts:77-91`) and its only repository call sites are test/fixture composition (`apps/agents-bridge/tests/capacity-planning-snapshot.integration.test.ts:91-113` and `packages/atlas-db/tests/semantic-batch-plan-ready-fixture.integration.test.ts:311-315,393-394`). It is not imported or instantiated by the production Bridge entrypoint.

The production Bridge composition creates only `createCapacityPlanningSnapshotReader()` from configured server credentials (`apps/agents-bridge/src/main.ts:25-45`) and exposes its one authenticated HTTP endpoint (`apps/agents-bridge/src/app.ts:57-69`). Credential bindings can authenticate a reader, including an isolated `qualificationVersion: "v2"` principal, but the configuration type and parser contain no consumer identity, consumer version, active-count, liveness, or readiness fact (`apps/agents-bridge/src/config.ts:84-102`; `apps/agents-bridge/src/capacity-planning-snapshot.ts:4-15,52-88`). The v2 principal is explicitly qualification-only and the v2 projection reports `productionActive: false` (`packages/atlas-db/migrations/0097_bssv201403_authenticated_calculated_capacity_snapshot.sql:1-4,188-197`).

The existing BSS activation epoch is authoritative for desired-admission-profile state, not application composition. It takes the per-domain advisory lock and writes an activation revision plus the active profile (`packages/atlas-db/migrations/0091_bssv20140202_shared_domain_calculated_allocation_publication.sql:253-270`), but hard-rejects the successor while the parent cutover is absent (`:257-259`). It cannot inspect a deployed IDSER process or its environment binding. Conversely, Bridge configuration is loaded and composed in the application process (`apps/agents-bridge/src/main.ts:12-45`), outside that database transaction. The repository therefore contains no authoritative mechanism that can represent and verify an *active IDSER capacity consumer*.

GHR remains intentionally terminal at this boundary. The semantic receiver returns only `parsed_only` (`apps/agents-bridge/src/ghr/routes/semantic/receivers/batch-plan.receiver.ts:17-43`), and the delivery worker records that disposition immediately after parsing (`apps/agents-bridge/src/ghr/delivery-worker.ts:184-200`). No IDSER continuation, NDV1 redemption, Better Auth session, SEM execution, or provider send is reached by this ticket.

This is an authority conflict, not a missing implementation detail: satisfying the frozen `RC-01405-05` literal “replacement” oracle would require manufacturing the nonexistent v1 production binding or treating test composition as production state. Both are prohibited by the ticket boundary and the user’s delegated direction.

## Proposed planning amendment (not yet authorized)

1. Reclassify `-05` as **initial v2 consumer activation**. Replace “remove/revoke the old active v1 consumer before the v2 consumer becomes active” with: “there is no active v1 consumer to migrate; historical v1 factories, reader code, and fixtures remain non-production-active and must not be composed, credential-bound, or reachable from the active IDSER planner.”
2. Replace the affected `RC-01405-05` pass condition with: exactly one authenticated BSS `CapacityPlanningSnapshot/v2` reader is bound to exactly one active IDSER v2 capacity consumer; the active composition has no v1 capacity consumer, v1 reader binding, adapter, fallback, dual read, prospective-to-qualified conversion, direct BSS SQL, or alternate capacity authority. Its proof is a production-composition inventory plus an authenticated actual-reader readiness integration, not an invented v1 removal event.
3. Retain `RC-01405-01..04` unchanged except that their actual-reader fixture must be exercised through that v2 consumer composition. In particular, its sizing acceptance is `inputTokens + reservedOutputTokens <= sizing.maxEligibleCompleteRequestTokens`, plus qualified input, output, context, request-byte, and applicable media bounds. IDSER owns reservation/buffer estimation and packing; BSS owns allocation, qualification, and runtime admission. TPM/concurrency division, borrowed immutable size, another tokenizer, and capacity synthesis remain forbidden.
4. Amend the parent gate so it requires: (a) accepted `-03` v2-reader evidence, (b) accepted `-04-03` BSS runtime-enforcement evidence, (c) a v2-only IDSER composition/readiness proof bound to the same authenticated snapshot identity, revisions, and fingerprint, and (d) a release record proving no v1 binding or alternate path. It must retain `bridge.activate_desired_admission_profile(...)`, its activation revision, and its fail-closed successor fence as the sole BSS activation authority.
5. Delete the claim of distributed atomicity. The release gate instead requires a verifiable fail-closed sequence: predeploy the v2 consumer in a non-active mode; prove its authenticated v2 readiness against the exact candidate without executing work; inventory zero v1 bindings; then, after the `-04-03` evidence and a successful readiness check, perform the existing serialized BSS activation. If the v2 reader is stale, non-qualified, mismatched, unavailable, or the consumer readiness check fails, do not activate; after activation, the consumer must stop/replan on any such result. The release record must bind the readiness observation to the activated profile/revision and snapshot fingerprint.

No new registry, table, service, scheduler, activation epoch, or compatibility lane is proposed. Source evidence does prove that no current durable mechanism represents consumer liveness. The proposed correction therefore treats readiness as an explicit, reviewable release-gate observation and requires the consumer to fail closed; it does not falsely describe that observation as database/application atomicity. A later planning decision may choose an authoritative cross-process attestation mechanism, but that would be a separate architecture change and is not authorized here.

## Required validation after an amendment

- Negative pre-activation: v2 remains isolated (`productionActive: false`); an IDSER v2 consumer receives a typed stop/replan result and BSS activation remains blocked. A v1 factory import, v1 credential binding, adapter, dual read, prospective conversion, direct SQL, or second capacity source fails the composition inventory.
- Positive activation: the sole authenticated v2 consumer reads a qualified, production-active snapshot bound to the selected activation revision/profile and canonical fingerprint, produces a fitting complete Semantic request, and leaves BSS attempts, reservations, quota/window state, jobs, transport, GHR delivery, SEM, and semantic truth untouched.
- Sizing boundaries: deterministic text/image/framing fixtures prove the exact complete-token inequality, request bytes, input, reserved-output, context, and media limits; each over-limit case stops/replans. The assertions prove no TPM-per-concurrency ceiling and that borrowing does not enlarge an immutable batch.
- Failure after predeployment: unavailable, stale, foreign, revoked, non-qualified, revision/fingerprint-mismatched, or non-active v2 data blocks planning with no fallback or effect.
- Parent gate: it rejects activation without the accepted BSS runtime evidence and the v2-only readiness record, and accepts only the matching release evidence. The test must also demonstrate that GHR still terminals at `parsed_only` and does not cause IDSER execution, SEM, or a provider send.
