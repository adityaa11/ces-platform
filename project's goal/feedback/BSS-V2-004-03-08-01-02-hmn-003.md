## Revised contract

### 1. Source relationship revision — before extraction

```text
ContextSourceRelationshipRevisionV1 {
  contract_version: "atlas.context-provenance/v1"
  relationship_lineage_id: deterministic ID for the immutable source-identity family
  revision: positive integer
  revision_hash: sha256(canonical immutable revision fields)
  scope: { project_id, workspace_id, document_id, source_sha256 }
  normalized_document: { execution_id, capability_identity, contract_version, profile_id_or_version }
  owned_source: { page_number, locator_type: "table", locator_id, source_unit_id }
  context_source: {
    page_number, locator_type: "visual_region", locator_id, source_unit_id,
    asset_ref, derived_asset_sha256
  }
  relationship: {
    type: "context_qualifies",
    direction: "context_source_to_owned_source",
    contextual_role: "title" | "legend",
    necessity: "essential" | "optional"
  }
  source_evidence: [identified accepted source/visual locators and evidence digests]
  proposal: {
    proposer_type: "atlas" | "provider" | "human_draft" | "other_policy_issuer",
    proposer_identity, model_or_profile_identity?, execution_or_run_identity?,
    confidence?, rationale_or_evidence_refs
  }
  disposition: "proposed" | "accepted" | "rejected" | "unresolved"
  authorization: { mechanism_id, attestation_id?, authorized_by?, authorized_at? } | null
  supersedes_revision_hash?: hash
  relationship_to_predecessor?: "challenges" | "refines" | "replaces"
}
```

No candidate ID appears here. `proposed` requires an identified source/evidence basis and provenance, but no reviewer authorization. The optional `confidence` is retained as fallible interpretation metadata and never changes `disposition` or authorizes use. `accepted` requires a future approved Atlas application validation/attestation path or another independently verifiable issuer admitted by an explicitly approved policy. A provider, model, asset reference, normalized locator, page relationship, geometry, or historical fixture declaration cannot provide that authorization.

### 2. Candidate binding revision — after extraction

```text
ContextRelationshipCandidateBindingV1 {
  contract_version: "atlas.context-provenance/v1"
  relationship_lineage_id
  source_relationship_revision_hash
  binding_revision: positive integer
  binding_hash: sha256(canonical immutable binding fields)
  extraction_execution_id
  table_owned_local_candidate_id
  candidate_evidence_refs: [the existing table and visual references]
  interpretation_state: "provisional_conditional" | "trusted_context_applied" | "not_applied"
  binding_validator: { identity, version, result, validated_at, rejection_code? }
  supersedes_binding_hash?: hash
}
```

This binding is append-only and references, rather than rewrites, the earlier source relationship revision. It must verify the same scope, source SHA, normalized-document identity, locator identities, derived-asset hash, and candidate evidence references. It cannot create a second candidate or promote a visual to a business assertion.

`provisional_conditional` is permitted only as non-canonical, reviewable interpretation state with the unresolved dependency recorded. It must not be represented as complete, accepted, or published Semantic V1 truth. `trusted_context_applied` requires an accepted source relationship, but still does not make the downstream semantic interpretation correct or canonically accepted; existing extraction and canonical-acceptance rules decide that separately.

## Authority and processing boundaries

| Matter | Permitted source | Effect |
| --- | --- | --- |
| Source/asset identity, SHA, locator, execution/profile | accepted NormalizedDocument and derived-asset authority | reliable source identity only; no semantic relationship authorization |
| Relationship hypothesis | Atlas/provider/human-draft proposal carrying attributable evidence and provenance | auditable `proposed` relationship; may inform only a provisional/conditional interpretation |
| Relationship authorization | future approved Atlas application attestation/review workflow, or later independently verifiable policy issuer | changes an existing revision to a separately recorded accepted revision; permits trusted contextual use |
| Interpretation quality | any later model/profile or human re-evaluation | creates a new proposal or binding revision; never overwrites original evidence/history |
| Semantic/canonical acceptance | existing Semantic V1 and acceptance pipeline | independent decision; no partial canonical acceptance is invented |

The runtime reviewer identity, permission checks, and application workflow are not implemented or claimed. Their absence does not block recording an untrusted proposal offline; it blocks only acceptance of that proposal as trusted relationship authority. Per-document HMN invocation is explicitly not a runtime prerequisite.

## Lifecycle, uncertainty, and progressive improvement

```text
identified evidence
  -> proposed relationship revision
       -> provisional_conditional interpretation (optional, non-canonical)
       -> accepted relationship revision -> trusted_context_applied interpretation
       -> rejected | unresolved (auditable; no trusted linkage)
```

- **Proposed:** may be wrong, incomplete, or challenged. It records its locators, source/asset identities, interpretation provenance, and uncertainty. An essential proposed relation cannot authorize canonical completion. Independent sources continue.
- **Accepted:** validates the relationship's authorized use as context, not the correctness of every semantic interpretation produced with it. It cannot skip normal extraction, evidence, reconciliation, or canonical acceptance gates.
- **Rejected/unresolved:** remain in the lineage with their reason and evidence. Essential dependents are blocked from authoritative completion; neither the hypothesis nor independent source progress is discarded.
- **Improvement:** a later model/profile/human review creates a new immutable proposal revision. It references the predecessor through `challenges`, `refines`, or `replaces`; source evidence, prior revisions, and prior outcomes remain intact. A fresh validator/attestation decision is required before a later revision can be trusted. No paid model, invocation, retry, or fallback is authorized now.

The identity hash for each revision includes the exact scope, normalized-document identity, source SHA, locators, asset identity/hash, contextual role/necessity, evidence identities, proposal provenance, predecessor reference, disposition, and authorization reference when present. It excludes only generated row identity and validation timestamp. A new proposal consequently cannot silently rewrite an earlier interpretation; a new acceptance decision cannot alter original source identity.
